## Nukta audit

A planned project spike: how much precomposed nukta is actually in the upstream data?

| Measure | Count |
|---|---|
| U+0B5C precomposed RRA in raw Odia strings | 0 |
| U+0B5D precomposed RHA in raw Odia strings | 0 |
| Rows containing either | 0 |
| Rows altered by `canonical()` | 0 |

**Result: none.** Aksharantar `ori` is already NFC and already free of the
precomposed forms, so `canonical()` is a no-op on this corpus. That is a fact
about this dataset, not a licence to drop the normalization: the invariant is
ours to guarantee, the artifacts are asserted canonical on write, and the next
data source will not necessarily be this clean.

### Nukta placement

The absence of the precomposed forms is only half the question; the decomposed ones
also have to be well formed. Every U+0B3C in the corpus, by the base it attaches to:

| Base | Codepoint | Occurrences | Verdict |
|---|---|---|---|
| `ଡ` | U+0B21 | 5,984 | legitimate |
| `ଢ` | U+0B22 | 856 | legitimate |
| `ଜ` | U+0B1C | 10 | **malformed** — passed through unchanged |
| `େ` | U+0B47 | 2 | **malformed** — passed through unchanged |
| `଼` | U+0B3C | 1 | **malformed** — passed through unchanged |
| `ଚ` | U+0B1A | 1 | **malformed** — passed through unchanged |
| `ଯ` | U+0B2F | 1 | **malformed** — passed through unchanged |

15 of 6,855 nukta occurrences sit on a base other than
DDA/DDHA. `canonical()` does **not** repair these: the sequences are already NFC-stable,
so they enter the lexicon exactly as upstream wrote them. Most are a nukta pressed into
service for /z/ in transliterated foreign names (`ଲୋଜ଼ନୋ`, *lozano*), which is defensible;
a handful are genuine corruption (a doubled nukta, a nukta after a vowel sign). The
volume is negligible and no row is dropped for it, but it is recorded here so that a
future odd-looking lexicon entry is traced to upstream rather than to this pipeline.

## Split discipline

The lexicon is built from **train + valid only**. The **test** split is written to
`core/test/golden/heldout.tsv` and never enters any lexicon artifact, so held-out
pairs are excluded by construction rather than by discipline.

Aksharantar itself repeats a small number of pairs across splits, and fuzzy
expansion can regenerate a test pair from a neighbouring key, so the build
explicitly deletes any lexicon row matching a test pair: **8 attested**
and **1 alias** rows were removed on this run. The build then asserts
that zero test pairs remain retrievable from any lexicon artifact, and fails if any do.

- Test pairs present as lexicon rows after the build: **0** (asserted).
- Test rows whose Odia word appears somewhere in the lexicon: 7 / 4,228 (0.2%).
- Test rows whose roman key appears somewhere in the lexicon: 192 / 4,228 (4.5%).

Those last two numbers define the in-lexicon versus out-of-vocabulary slices that
`CLAUDE.md` requires the evaluation to report separately.

## Weighting, and the IndicCorp substitution

`plan/01-engine-design.md` calls for unigram frequencies from IndicCorp v2. That
corpus is far too large for this pass, so **`unigrams.tsv` is derived from
Aksharantar attestation instead**. This is a substitution and it is a real
limitation, stated here rather than discovered later:

- Every (roman, Odia) pair in the release is **unique**, so raw attestation counts
  are all 1. There is no count signal to log.
- Record order is shuffled, not frequency-ordered (mean word length and mining
  score are flat across all ten deciles of the file), so rank carries no signal.
- The highest-frequency Odia function words are **absent from the dataset**
  altogether. Aksharantar samples mid-frequency content words; mean Odia word
  length is 8.8 characters, i.e. long inflected forms.

What the data does contain, and what the weights therefore use:

| Signal | Detail |
|---|---|
| pair provenance | `Wikidata` 3, `Samanantar` 2, `AK-Uni` 1.5, `AK-Freq` 1.5, `AK-NEI` 1.5, `AK-NEF` 1.5, `IndicCorp` 1 |
| mining confidence | `score`, present on IndicCorp pairs only, observed range [-0.3500, -0.0015], rescaled to [0.5, 1] |
| attestation multiplicity | number of distinct romanizations of a word, 1 to 5 |

```
pair_weight  = source_weight * (0.5 + 0.5 * normalized_score)
alias_weight = pair_weight * 0.6
word_weight  = sum of pair_weight over every pair attesting the word
logfreq      = ln(1 + word_weight)          <- NOT a corpus frequency
```

`logfreq` is an attestation weight wearing a frequency-shaped column. Treat it as
a weak prior only, and replace it with a real IndicCorp v2 unigram count before
drawing any conclusion about ranking quality.

## Fuzzy key expansion

Alias keys are generated at build time so the runtime stays a plain lookup with no
edit-distance code in the hot path. Each rule below is applied on its own, plus one
fully-collapsed skeleton; aliases carry 0.6x the weight of the attested spelling and never displace it.

| Rule | Example |
|---|---|
| collapse doubled letters | `chhatar` -> `chatar` |
| `aa` -> `a`, `ee` -> `i`, `oo` -> `u` | `sahityaanurageemane` -> `sahityanuragimane` |
| `v` -> `w` and `w` -> `v` | `samworbdhita` -> `samvorbdhita` |

## Everyday lexicon and the merge

Added after the Aksharantar build, by `tools/build-data/build_common_lexicon.py`
(Python 3 stdlib), on 2026-10-04. Input: `core/data/webfreq.tsv` (sha256
`0d3049dd420058e26b4dd9ae16a59c59929daa49c4da7edf75f6f4bd5716d8d2`), whose provenance is in
`PROVENANCE-webcorpus.md`. It does two things.

**1. Romanize the top web-corpus words.** It covers the top 120,000 types for
`lexicon-common.tsv` and the top 30,000 for `lexicon-common-web.tsv`. Each word gets
the spellings a person plausibly types: long vowels collapsed, `ee`/`oo`, a dropped
final `a`, `v` for `w`, `ri` for `ru` on vocalic words, and nasal-cluster collapse.
The weight is `ln(1+count) / ln(1+peak) * 2.303`. The **exact** romanization gets
the full weight and every looser variant gets 0.9x.

**`j`-keys for ଯ (2026-10-04, V2.1).** ଯ is romanized `y`, but Odia pronounces it
*ja*. A word that starts with ଯ therefore also gets every one of its spellings with
the initial `y` replaced by `j` (ଯିବା: `jibaa`, `jiba`, `jib`), weighted 0.9x like
the other loose spellings; the exact key stays `y…`. Only a word-initial ଯ: inside a
word the letter is ୟ, which really is `y`. This adds 4,971 rows to
`lexicon-common.tsv` and 1,381 to `lexicon-common-web.tsv`; after the merge, 4,495
new and 110 raised rows in `lexicon.tsv`, 1,351 new and 8 raised in
`lexicon-web.tsv`. No other row changed. Trade-off: where a `j` spelling is shared,
the more frequent word leads (`je` → ଯେ 81,614 over ଜେ 1,716); see the commit
message for every ଜ-word that lost first place.

"Exact" is the careful spelling with ଂ → `m` and ଁ → `n`. That matches the careful
register of `tools/eval/everyday.ts`. `docs/romanization-reference` accepts both `n`
and `m` for ଂ. When a word has an anusvara or candrabindu, `ଂ`→`n` and the dropped
sign are variants. Treating all three expansions as exact was tried. It
gave identical held-out and everyday metrics, so the single-exact definition was kept.

Until 2026-10-04 the build was **not reproducible**. The full-weight form was
`variants(...)[0]`, the first element of a Python `set`, so it changed with
`PYTHONHASHSEED`. The `ri`/`v` variants also branched off a seed picked by set
order. A rerun of the unchanged script changed about 31,000 of 88,193 rows in
`lexicon-common-web.tsv`. Both now use the exact form and `variants()` returns a
sorted list. Output is byte-identical across hash seeds and across reruns.

**2. Merge into the lexicons the engine loads.**

```
lexicon.tsv      = lexicon.tsv.aksharantar-only      ∪ lexicon-common.tsv
lexicon-web.tsv  = lexicon-web.tsv.aksharantar-only  ∪ lexicon-common-web.tsv
```

For each (key, word) pair the merge keeps the higher weight. It writes one
`# romanKey\todiaWord\tweight` header, sorts keys ascending and then weight
descending (equal weights keep input order), and formats weights as `{w:.4f}`.
Odia is passed through `canonical()` on read and asserted canonical on write. The
`.aksharantar-only` inputs are only ever read, so the merge is idempotent. On the
pre-fix common files, this merge reproduces the earlier committed
`lexicon.tsv`/`lexicon-web.tsv` byte for byte.

**Order matters.** `build_lexicon.py` still writes `lexicon.tsv`, `lexicon-web.tsv`
and this file directly. After rerunning it, rename its two lexicon outputs to
`*.aksharantar-only`, run `build_common_lexicon.py`, and restore this section.
